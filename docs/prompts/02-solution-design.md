# Prompt：方案设计

**必须使用 Superpowers skill**：继续 `brainstorming` 流程（输出方案设计文档并提交）。
方案经人工确认后，**必须调用 `writing-plans`** 创建实现计划——这是进入任务拆分的唯一合法路径。

基于已批准的需求文档，创建或 review 方案设计。

不要写代码。

重点检查：

- 分层边界
- 数据流
- 状态模型：3 个以上业务状态必须显式列出状态枚举、合法流转和非法流转
- realtime、异步或 webhook 行为
- 权限和可信边界：前端、客户端参数、URL、localStorage、webhook payload 原文都不是可信来源
- 代码结构边界：入口层、handler / service / workflow 层、数据访问层分别负责什么
- 扩展方式：多命令、多类型、多策略分发是否需要 registry / handler map / strategy / adapter
- 结构风险：入口变胖、分支堆叠、重复上下文读取、重复输出拼接
- 副作用边界：请求、写入、订阅、导航、全局状态修改分别在哪里发生
- 幂等性：webhook、支付、KYC、合约事件、数据库写入必须说明幂等键和重复处理
- 错误处理：用户反馈、日志 / 监控、重试、降级和阻断策略
- 数据访问：表、字段、RLS / 权限、索引、事务或一致性要求
- 性能影响：列表、realtime、轮询、hook、provider、context 或全局状态变更
- 配置和密钥：新增 env var 的用途、作用域、是否客户端可见
- 兼容和回滚：schema、接口响应、状态枚举或外部回调格式变更
- Open Questions Resolution：逐条闭环需求文档中的开放问题，标明是否阻塞实现
- Decision Notes：记录方案相对需求假设的修正、取舍原因和后续影响
- Consistency Check：检查需求与方案中的文件路径、编号、字段名、权限模型、数据读写路径和范围边界是否一致
- 失败模式
- 风险标签对应的安全、性能、数据和最佳实践门禁
- 备选方案
- 测试策略影响

输出：

- 更新后的方案设计文档
- 关键决策和原因
- 需求开放问题的处理结论
- 一致性检查结果；如果发现冲突，说明采用哪一侧以及原因
- 阻塞实现的开放问题，如有
