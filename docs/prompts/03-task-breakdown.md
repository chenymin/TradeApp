# Prompt：任务拆分

**必须使用 Superpowers skill**：`writing-plans` 主驱动。
每个 Task 粒度为 2-5 分钟可完成一步（写测试 / 运行验证 / 实现 / commit 各为独立步骤）。
计划完成后立即选择执行模式并告知用户：
- 当前 session 执行 → 调用 `subagent-driven-development`
- 新 session 独立执行 → 引导用户在新 session 调用 `executing-plans`

基于已批准的需求文档和方案设计，创建实现计划。

按业务场景拆任务，不要只按文件拆。

每个任务必须包含：

- 业务场景
- 范围内
- 范围外
- 预计影响文件
- 结构约束：入口层是否允许改、handler / registry / strategy 新增位置、领域逻辑位置
- 结构验收标准：入口不变胖、无大型 if/else / switch 堆叠、重复逻辑集中处理
- 模块内聚与可测试性约束：模块单一职责、业务规则 / IO / 副作用 / UI 展示 / 数据转换分离、核心逻辑可独立测试
- 代码规则约束：状态机、可信边界、副作用、幂等性、错误处理、数据访问、性能、测试追踪、抽象、模块内聚、可测试性、配置密钥、兼容回滚
- 代码规则验收标准：每条适用规则都有明确实现位置和验证方式
- 验收标准
- 测试
- 对需求文档的可追溯关系

实现计划必须包含：

- Decision Notes：继承方案设计中的关键决策，说明具体实现影响
- Forbidden Patterns：列出本需求禁止出现的实现方式、API 调用、数据访问路径或结构漂移模式
- Machine Verification：为关键路径、禁止模式、文件存在性和测试补充可执行命令
- Consistency Check：检查需求、方案、实现计划的路径、编号、字段名、权限模型和验收标准是否一致
- Final Verification Required：列出完成前必须运行并汇报结果的 typecheck、测试、反模式扫描、路径扫描和手动 QA

输出：

- 更新后的实现计划
- 推荐优先实现的第一个 task
- 依赖关系或执行顺序风险
- 一致性检查结果；如发现需求与方案冲突，必须引用 Decision Notes 说明采用的决策
